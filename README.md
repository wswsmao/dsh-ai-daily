# AI技术日报插件

固定业务流程，不让调度模型决定查哪些词或是否偷省步骤。

## 组成

- `ai_daily_run`启动完整或collect-only后台运行；`ai_daily_job`查看/取消/续跑/重试发布通知/setup只读发现。
- `ctx.aiDaily`内部服务被定时任务固定动作 `ai-tech-daily`直接调用。
- `ctx.wechatSearch`提供串行原始关键词检索、同一reference_time和正文采集。
- 英文一手来源RSS/Atom固定配置；逐源记录成功失败和时间范围。
- LLM通过现有DSH模型适配器逐篇/逐块读取，无工具；固定schema和引文校验，不因模型遗漏少做文章。
- 本地归档独立Git；公开网站只允许投影后的摘要、标题、署名、日期、来源链接和覆盖说明。
- GitHub Pages推送核验网页版本标识后才通知微信；发送结果不确定不自动重发。

## 项目目录

`D:\Program Files (x86)\dsh-deploy\archive\daily\ai-tech-daily`。

本插件代码独立Git，不修改DSH源码；已有定时任务和微信插件分别扩展并各自提交。无MCP、无额外Skill；内容处理规范固定存config/editorial-policy.md，由程序强制读取。

## 运行

固定日报每天12:10北京时间，回溯2天。**只采集微信公众号内容**（非微信来源已移除）。执行清单在config/queries.json，来源清单 config/sources.json 现为空。每次冻结配置及统一时间窗，不设文章返回数上限。

关键词按中文技术圈写法：术语保留英文原词（agent harness、AgenticOS），其余用中文短语；单个词不够精准时用「AI + 上位词」词组（AI 硬件、AI 基础设施）。

采集流程：先取列表（不打开任何文章）→ **模型初筛**（标题/摘要）→ 只打开通过的文章 → 模型分析与评分。这样明显不合格的条目（如"某某院士发言"）不会消耗一次完整打开。

采集与模型分析**流水线并行**：采集受微信单窗口限制保持串行，分析并发进行（默认 8），采集结束后等待分析收尾。

运行预算 `runtime_minutes` 是硬截止：超时后未完成阶段标 `partial` 且 `stop_reason=RUNTIME_BUDGET_EXCEEDED`，绝不假称完成。模型调用预算 `max_calls` 触及后停止调用并把相关文章标为处理失败，同样传导为 `partial`。

工具`ai_daily_job setup`只读显示查询配置、发布配置和IM安全目标元数据，不读取Secret。首次配置需要已批准GitHub账号及IM目标，所有凭据不进Git。

## 阶段语义

collection → analysis → archive → site → publication → notification，各阶段独立状态。

### 采集的三段式（用户明确要求的顺序，不可改动）

这是产品的核心流程，实现必须严格按此顺序：

1. **A1 全部搜索**：12 个关键词**逐个搜索**，每个关键词的搜索结果列表写入临时文件
   `pool.json`（含 `keyword` 字段标明来源），**不打开任何文章、不做任何判断**。
   微信只有一个搜索窗口，所以"保存页面"= 保存列表数据，不是保存窗口。
2. **A2 统一初筛**：所有关键词搜完后，把**整个池子**一次性交给模型判断类型。
   一次判断能看到全部候选，因此跨关键词的同一事件能被识别；每个候选都带 `keyword` 字段。
3. **B 逐篇打开 + 分析**：只对初筛保留的候选逐个打开（每个关键词需要重新搜索以定位列表行），
   每打开一篇立即送模型分析，采集与分析并发。

**反例（实现偏离过，禁止重演）**：每搜完一个关键词就立刻初筛它——这样模型只能看到单个关键词的
列表，跨关键词的重复事件无法识别，也不符合"统一池子"的语义。

### 判断环节一律走文件（初筛 / 跨日重复 / 选稿）

需要模型判断的环节不把数据塞进 prompt。流程固定为：

1. 代码把本次输入写成 `<name>-input.json`
2. 子 agent 用 read 读这个文件，自己决定分几次读、按什么顺序看
3. 子 agent 用 write 把结论写到 `<name>-output.json`
4. 代码读输出文件继续下一步，**不解析回复文本**
5. 进度写 `<name>-progress.json`，中断后能看出跑到哪一步

这样一次判断的规模由 agent 自己的读法决定，不再受单次请求的上下文或输出上限约束。因此
`max_output_tokens`、`batch_size`、`batch_chars`、`batch_article_chars`、`prescreen_max_calls`
这些为"防超限"存在的参数已经移除；单次分析调用所需的内部上限是 `analysis.js` 里的常量。

**拿不到 agent 一律报错，不降级。** 判断环节的输入规模已经超出单次请求能承载的范围，把数据重新
塞回 prompt 只会得到被截断的判断结果，比失败更难发现。`*-progress.json` 会留下 `failed` 与原因，
便于定位是宿主未提供 `subagents`、provider 缺失，还是子 agent 未写出输出文件。跨日重复判断是例外：
它失败时保持文章可发布，因为未判定的文章不应被当成重复。

初筛失败同样不再"全量放行"：跳过判断直接打开所有候选，会把预算花在没人筛过的文章上，因此该查询
直接失败并把原因写进 trace。

### 保留策略（候选池 → 日报）

池子装的是**已经打开并分析过**的文章（有正文、有分类、有摘要、有打分）。

**最终选稿是一次整体判断**：把整个候选池连同目标、名额、以及「同一件事只留一篇」这条规则交给
一个 agent，由它决定留哪些。**代码不指导它怎么排序、怎么比较、怎么处理并列**——那正是需要全局
视角的地方，拆成按类别或按分段的多次调用反而会丢掉这个视角。

- **池子 ≤ target**（默认 30，可配置）：不调用模型，**几乎全部保留**；仅剔除低于
  `min(分数线, 4)` 的文章——空席位不值得用一篇垫底文章去填。
- **池子 > target**：一次 agent 判断选出 target 篇，名额按 `ratio` 给出。
- 判断失败或返回空集时保留整个池子并记录原因——空日报比满日报更糟。

### 周报

`profile: weekly` 复用日报的全部策略，只覆盖时间窗（7 天）与目标篇数（60），归档到
`reports/weekly-` 前缀目录，标题追加「· 周报」。关键词、初筛策略、分类比例、模型选择与日报共用。

### 异常处理

判断链路上任何一步失败都直接报错，不降级：拿不到子 agent、子 agent 未产出、初筛出错，都会让该查询
或整轮失败，并在状态里留下可定位的原因。

少数操作不允许中断整轮——清理旧 run、核对残留状态、取采集器句柄、单篇分析失败后保留原文——这些不
抛出，但**一律写入 `state.tolerated`**，包含时间、位置与脱敏后的原因，上限 200 条。单篇分析失败的
记录汇总在 `state.analysis_warnings`。这样"没中断"和"没发生"在事后可以区分。

日志内容经过 `safeError` 脱敏：URL 与 `token=`/`secret=` 之类的值会替换掉，不会把凭据写进状态文件。

### 临时文件保留期

`retention.temp_retention_days`（默认 30）。每轮开始前清理超期的 run 目录与运行时散落文件。
**永不清理**：`reports/` 归档（产品本身）、`article-index.json`（跨日去重历史）、
`deliveries.json` / `occurrences.json`（投递与幂等记录）。

- `complete`：本次计划与文件/发布/通知全部完成；不等于全网完整。
- `partial`：计划全部处理但存在采集/正文/模型处理缺口，网页说明缺口。
- `blocked`：尚需发布授权、IM目标或某阶段失败。
- `cancelled/interrupted`：保留检查点，续跑同一时间窗。

同一schedule_occurrence重放只返回同一run_id；同日修订采用版本链接不覆盖已分享版本。相同文章跨日按identity和内容指纹复用处理，修改内容可重新处理；事件聚合保留不同分析与原文链接。

续跑语义：`resume` 不带 stage 时递增版本并重跑 archive/site/publication/notification（不重复检索）；`retry-publication` 复用已渲染目录重发，**不重新渲染**，靠 sha256 与版本标识校验文件未被改动，也不会覆盖已分享的版本链接——如需重渲染请用不带 stage 的 `resume`。`retry-notification` 仅在 publication 已 `verified` 完成后才允许，且先前投递结果未知时标 blocked 而不自动重发。

事件聚合只接受可核验身份：模型给出的 `event_key` 必须对应文章自身的 arXiv 号、GitHub 仓库、release tag 或版本号才用于聚合，否则回落为单篇文章；组内成员缺少该身份时会拆散，避免公开页面出现错误归属。

## 🧠 内容判断原则（重要）
**涉及内容理解的部分，禁止用代码分析（正则/关键词计数），只能由模型判断。**

理由：正则只做表面匹配。营销文写"重磅发布，性能提升 100 倍"会全命中给高分（实际是垃圾）；
真论文措辞平实没写"局限"会被扣分（实际很好）。

分工：

| 环节 | 由谁做 |
|---|---|
| 初筛（是否低价值类型） | 模型 |
| 5 维评分（新颖/具体/深度/一手/诚实） | 模型 |
| 同信息点成对对比（优中选优） | 模型 |
| status / topics 等分类判断 | 模型（代码不推翻） |
| 去重、配额、排序、统计 | 代码（确定性逻辑） |
| 安全/格式/URL/SSRF 校验 | 代码 |

代码可以保留**字符串事实核查**（如引文是否真的出现在正文里，防模型编造），
但**不得据此推翻模型的判断**，只能标记供后续参考。

## 安全边界

正文是引用数据，不执行正文中的安装/联网/发送指令。没有完整读取则uncertain；每个块都处理，不接受丢ID。网站不带原始正文、绝对本地路径、私人日志、投递路由或凭据。发布工作区单独Git且只有allowlist文件可push，禁止forcepush。

模型事实准确性不能保证不同模型完全等同；程序保证执行清单、处理条目、引文一致性及明确缺口。网络和微信索引之外的全量不保证。
